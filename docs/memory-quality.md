# Memory admission and provenance

Memory topics remain Markdown files with frontmatter under `$TACO_HOME/memory/projects/<workspace-key>/`. The body covers one coherent durable theme, starts with its conclusion, and may include scope, reasons and exceptions as headings or lists. The hard limit is 2,000 characters; concise facts may be much shorter. Only topic summaries enter the main model context; the user-level `MEMORY.md` is still injected in full.

Automatic extraction defaults to no write. Every action needs a durable basis and an exact quote from a new visible user message. Prior conversation text helps resolve references but cannot supply new evidence. Original entry identities and a persisted session cursor prevent repeated extraction across runs and compaction. Long backlogs are evaluated chronologically within an 8,000-character input budget; later messages remain for subsequent runs. Oversized messages retain a persisted character offset and continue from that offset after restart; failed model or storage calls retain their input progress. Existing-topic input is capped at 24,000 characters. Replacements require complete old content, and uncertain new additions are suppressed when topic summaries are omitted.

Both background calls mount one result-only tool: `submit_memory_extraction` for automatic add/update decisions and `submit_memory_dream_plan` for consolidation. They consume validated tool arguments directly; JSON embedded in prose or Markdown is not accepted. Exactly one correctly named tool call must complete, with no argument parsing error, unknown fields, invalid schema, or unfinished/failed response. Submission validation also enforces string limits in UTF-16 units to match storage and metadata checks, including supplementary Unicode characters. An explicit empty `actions` array is a successful no-op. Extraction accepts at most three actions; dream accepts at most forty. Invalid submissions retain extraction progress or fail the dream run without stamping success. The lite-model fallback applies the extraction submission validator, so valid tool-only output succeeds and invalid lite output retries on the main model. Text-only consumers such as session titles retain their existing response criteria.

Result tools submit proposals rather than writing memory. Evidence admission, runtime-supplied provenance, full-content replacement checks, consolidation previews, retirement limits and compare-and-swap writes still run after schema validation. Models that return text instead of calling the result tool fail visibly in dream or leave extraction evidence pending; the current provider-neutral API does not offer a required-tool choice. Consolidation keeps its 240-second per-call, 270-second scheduled model budget and 300-second scheduler timeout.

Each stored source records `sessionId`, `recordedAt`, `via` (`auto` or `tool`), and optional `entryId`. Runtime code supplies identity. The memory tool carries its session identity through an in-process async context, not a public RPC parameter. Updates union sources; dream merges inherit the union of actual source topics. Legacy files retain absent provenance. `read` exposes frontmatter; the deferred `sessionRead` tool can page through visible user/assistant text in a source session, with the existing local-main and workspace boundary. Removed sessions can no longer be read.

Identical content and metadata do not refresh `updatedAt`; additional source evidence can persist without changing ranking. Replacements and dream rewrites can update stale names and descriptions. Dream still supports previews, reversible archive/restore, bounded retirement and conflict detection. Eligible workspaces are consolidated at most once per `minHours` (24h by default) as long as they hold at least three topics; there is no topic-change threshold. Oversubscribed dream prompts reserve a rotating cold-topic share.

`packages/sidecar/tests/memory/admissionCases.ts` contains positive/negative semantic examples. Deterministic tests cover structural admission, fresh-evidence identity, source propagation, retries, budget boundaries and concurrent edits. These tests use model stubs; they do not measure real model precision. To evaluate prompt changes, run these examples against the configured extraction model and record unnecessary-write and missed-durable-fact rates separately. Require an exact supporting user quote and inspect whether the stored scope exceeds that quote.

Extraction logs report input size, elapsed time, candidate/admitted/rejected counts, writes, unchanged actions and provider usage when available; no conversation or evidence text is logged. After a failed evaluation the next attempt waits a doubled cooldown (capped at 32× the 5-minute base), so a provider that never calls the result tool does not re-bill the same batch every five minutes. Numeric expiry policies and a separate fact-confirmation timestamp are follow-up changes, rather than part of this implementation.
