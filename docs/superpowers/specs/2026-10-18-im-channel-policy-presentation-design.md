# IM 渠道策略呈现与继承语义设计

日期：2026-10-18
状态：已确认设计，待实施

## 目标

优化渠道策略和会话策略的配置体验，同时兼顾偶尔配置的管理员和经常维护多个渠道的高级管理员。用户打开策略面板后应能直接回答两个问题：

1. 当前实际生效的值是什么？
2. 这个值来自上级策略，还是由当前层单独设置？

渠道层和会话层使用同一套交互。渠道层的上级是全局策略或系统默认，会话层的上级是渠道策略。界面不再把内部枚举 `ask`、`deny`、`off` 暴露为“继承(ask/deny/off)”这样的术语。

## 已确认的策略语义

### 单值字段

以下字段都支持“跟随上级”和“当前层单独设置”：

- 文件工具：允许 / 拒绝
- Shell：允许 / 拒绝
- 命令审批模式：手动审批 / 自动审批
- 会话独立 scratch 目录：开启 / 关闭
- 执行目录：指定目录 / 跟随上级

“跟随上级”表示当前层不保存该字段。当前层已经保存的字段可以恢复为跟随上级；恢复操作会删除当前层该字段，而不是保存一个复制出来的上级值。

### 命令规则

白名单和黑名单在每一层都采用追加语义：当前层只能增加规则，不能通过编辑当前层规则移除上级规则。最终规则集合按层级合并：

```text
全局规则 + 渠道新增规则 + 会话新增规则
```

黑名单优先于白名单，继续沿用新的命令审批体系。规则区域的说明必须明确写出：

> 当前层规则会在上级规则基础上追加；黑名单优先。

当前层添加的规则可以删除；上级规则以只读方式显示。清除当前层新增规则后，该层仍然可以保留其他字段的单独设置。

这要求服务端的策略解析也使用追加语义。当前实现的 `mergeImWorkspacePolicy` 对 `commands.allow` 和 `commands.deny` 是字段替换，导致会话层写入列表时可能遮蔽渠道层列表；实现阶段必须修正为按层追加，同时保持单值字段的覆盖语义。

## 交互设计

### 页面头部

策略面板顶部显示当前范围和上级关系：

```text
渠道策略 · 企业微信
上级：全局权限策略
```

```text
会话策略 · 张三
所属渠道：企业微信
上级：企业微信渠道策略
```

渠道面板继续展示该渠道下存在单独会话设置的会话摘要。摘要包括会话标识和单独设置项数量；展开后可以进入统一的会话策略面板。无路由的孤儿覆盖继续提供清理入口。

### 单值字段卡片

每个单值字段采用“状态 + 来源 + 操作”的结构，而不是把“继承”作为一个下拉选项：

```text
命令审批模式                         跟随上级
手动审批
来源：全局权限策略

[为此渠道单独设置]
```

点击“为此渠道单独设置”后，卡片展开可选值：

```text
命令审批模式                         此渠道单独设置
[手动审批                    ▼]
来源：此渠道

[恢复跟随上级]
```

覆盖状态下，当前值与来源必须同时可见。恢复操作明确写成“恢复跟随上级”，避免用户把“手动审批”和“继承(ask)”误认为两个不同的审批模式。

状态卡需要支持紧凑模式：高级管理员可以展开所有字段进行连续配置；默认模式只展开有本层覆盖的字段，其余字段显示生效值和来源。

### 规则区域

规则区域分为两个固定区块：

```text
新增白名单                         本层新增
上级规则：ls、git status             只读
本层新增：git diff                  可删除

新增黑名单                         本层新增
上级规则：bash *                    只读
本层新增：rm -rf *                  可删除
```

没有本层规则时显示“暂无本层新增规则”，而不是显示“暂无规则”，避免用户误以为上级规则不存在。添加规则的输入框和删除按钮只作用于本层新增规则。

### 文案映射

UI 层统一使用产品文案：

| 内部值 | 展示文案 |
| --- | --- |
| `ask` | 手动审批 |
| `auto` | 自动审批 |
| `allow` | 允许 |
| `deny` | 拒绝 |
| `on` | 开启 |
| `off` | 关闭 |

内部值只能用于协议和状态判断；不能直接插入“当前值”“来源”或辅助说明。

## 数据与组件设计

### 策略解析

保留现有三层结构：

```text
系统默认 / 全局策略 → 渠道默认 → 会话覆盖
```

解析规则分为两类：

- 单值字段：后层有值时覆盖前层；未设置时继续使用上层。
- 命令规则：各层列表拼接；黑名单和白名单分别去重；评估时黑名单优先。

服务端继续 fail-closed：某层策略损坏时忽略该层并使用有效的父层。规则列表损坏时应只丢弃损坏层的规则，不影响父层的单值权限和规则。

### 管理接口

现有 `imPolicy.get` 已返回原始的渠道和会话 patch，以及 resolved policy。为支持稳定展示来源，接口需要补充面向 UI 的来源信息，或者提供等价的可推导数据：

- 每个单值字段的有效值和来源层级。
- 当前层新增规则与上级累计规则的分组结果。
- 当前层是否存在覆盖，以及恢复该字段所需的清除动作。

来源信息应由服务端依据同一套解析逻辑生成，避免桌面端复制一份层级合并规则后与 sidecar 产生分歧。协议类型应使用稳定的来源枚举，例如 `default`、`global`、`channel`、`chat`，展示文案由桌面端国际化处理。

### 桌面组件

建议拆出三个职责清晰的组件：

- `PolicyScopeHeader`：显示当前范围、上级关系和策略层级。
- `PolicyValueCard`：显示单值字段当前值、来源、覆盖和恢复操作。
- `PolicyRuleLayers`：显示上级累计规则与本层新增规则，维护本层规则。

`ImPolicyDialog` 负责加载、保存、确认和布局；不再直接把每个字段都建模为 `INHERIT` 下拉项。保存时只发送本层真正设置的字段；恢复字段时发送明确的字段清除操作，不能用“复制上级值”代替。

## 数据流与保存行为

```text
imPolicy.get
  → 服务端解析策略值、来源和规则层级
  → 桌面端显示生效状态
  → 用户选择当前层覆盖或新增规则
  → 只提交当前层变更
  → 服务端校验并持久化 patch
  → 失效受影响 IM workspace
  → 广播 im.policy_changed
  → 打开中的面板重新拉取
```

保存一个字段不能清除同一层的其他字段。保存规则时只能修改当前层新增规则。清除会话覆盖时，当前会话所有字段恢复到渠道层；清除单字段时，只删除该字段并保留同层其他覆盖。

保存策略会立即影响后续工具调用，并可能中断正在进行的对话，因此继续保留保存确认提示。读取失败、保存失败和规则校验失败使用现有错误提示机制；失败时保留用户当前编辑状态，避免重新打开面板才能恢复输入。

## 兼容与迁移

- 继续接受磁盘上的旧 `commands.rules`，由现有配置规范化逻辑转换为白名单。
- 旧策略文件中缺少字段时继续按层级回退。
- 已存在的渠道和会话 patch 不需要一次性重写；读取时按新的规则追加语义解析。
- 桌面端不应再把 `__inherit__` 作为用户可见选项。若协议仍暂时使用 patch 中的字段缺省表达继承，哨兵值只能存在于组件内部，不得进入保存 payload。

## 验证要求

### 策略层

- 单值字段仍按默认 → 渠道 → 会话逐层覆盖。
- 渠道和会话规则都能追加到父层，且子层规则不会遮蔽父层规则。
- 白名单与黑名单去重，黑名单命中时优先拒绝或要求审批的现有行为不变。
- 清除单字段只删除该字段；清除整个会话覆盖后回到渠道策略。
- 任一层损坏时，父层有效单值和规则仍然保留。
- 保存策略后 workspace 失效和 `im.policy_changed` 推送行为不变。

### 桌面端

- 渠道和会话范围共用同一套值卡片与规则分层组件。
- 默认状态能显示“当前值”和“来源”，不出现原始 `ask`、`deny`、`off`。
- 覆盖、恢复和本层规则增删都会生成正确的 patch。
- 渠道页能显示会话覆盖摘要，并能清理孤儿覆盖。
- 全局、渠道、会话三种来源的文案都有中英文翻译。

## 非目标

- 本次不重做全局权限设置页的整体布局。
- 本次不引入新的审批风险等级或新的命令匹配语法。
- 本次不允许会话层移除全局或渠道的黑名单规则。
- 本次不把渠道策略与普通文件 workspace 的权限模型合并为同一份存储。
